## ROOT_CAUSES

### Android double UI

**PRIMARY**
- `components/IncomingCallListener.js:218-234` (`showCall`) always calls Android `callKeep.displayIncomingCall(...)` even when `AppState.currentState === 'active'`, then `components/IncomingCallListener.js:238-239` sets React state and renders the JS modal. Foreground WS `call_invite` enters here via `components/IncomingCallListener.js:319-418`.
- `components/IncomingCallListener.js:397-418` tries to dismiss native UI before `showCall`, but `showCall()` immediately starts it again. Also `Notifications` is undeclared at `:413`, and `NativeModules.IncomingCallModule.dismiss` has no matching native module in supplied Android code.

**CONTRIBUTING**
- `modules/.../CallRingingService.kt:98-116` starts foreground notification untagged, but avatar refresh at `:127-135` calls `nm.notify("call_notification", id, ...)`, creating/updating a separate tagged notification.
- `modules/.../CallNotificationService.kt:196-199` cancels only tagged notifications; it does not cancel the untagged foreground-service notification.
- `modules/.../CallFirebaseMessagingService.kt:65-68,145-164` foreground detection only checks module flag + `IMPORTANCE_FOREGROUND`; misses visible/resume races and module-not-created cases.
- `components/IncomingCallListener.js:53-58,211-216,375-379` force-resets `_callActive = false`, defeating `/call`’s suppression state.

### iOS unidirectional audio / callee uplink dead

**PRIMARY**
- `modules/.../ios/ExpoCallKitModule.swift:379-397` emits `onCallAnswered` before `CXAnswerCallAction.fulfill()` and before `provider(_:didActivate:)`. JS can create PC/addTrack while WebRTC has not observed the CallKit-owned active audio session.
- `modules/.../ios/ExpoCallKitModule.swift:455-507` forwards `audioSessionDidActivate:` best-effort but then calls likely-wrong `setIsActive:`; WebRTC expects manual audio + `isAudioEnabled = true` (`setUseManualAudio:`, `setIsAudioEnabled:`). Also uses `.allowBluetoothA2DP`, which is output-only and can kill mic route.
- `app/call.js:704-744,777-800` subtle remaining `recvonly` path: `waitForLocalTracks()` can `replaceTrack(audioTrack)` onto an existing `recvonly` transceiver, then pre-answer audit skips `direction='sendrecv'` because `sender.track === audioTrack`. Answer SDP can remain `recvonly`.

**CONTRIBUTING**
- `components/IncomingCallListener.js:636-653` JS tries to activate audio session before CallKit completes activation, and calls non-standard `audioSessionSetActive`.
- `modules/.../ios/ExpoCallKitModule.swift:509-517` does not forward `audioSessionDidDeactivate:` / disable WebRTC audio.
- `modules/.../ios/ExpoCallKitModule.swift:60-74,455-474` audio category options are inconsistent between pre-arm / answer / didActivate.
